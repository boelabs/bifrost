---
title: "Estado específico del proveedor"
description: "Conserva las firmas y el estado opaco necesarios para continuar una conversación."
---
Algunos proveedores devuelven estado opaco que debe reenviarse sin cambios en el siguiente turno. Bifrost lo conserva **a través del cliente, sin almacenarlo en el servidor**. Hay dos tipos:

- **Estado vinculado a la llamada de herramienta**: firmas de pensamiento de Gemini. Gemini 3 rechaza una solicitud de seguimiento cuyas llamadas de función reproducidas carecen de su `thoughtSignature` (`400 INVALID_ARGUMENT`).
- **Estado vinculado al mensaje**: reasoning cifrado OpenAI (elementos `reasoning` con `encrypted_content`), que mejora la calidad del uso de herramientas de múltiples turnos cuando se reproduce; firmas de Gemini en respuestas de texto, que Google recomienda reenviar para mantener la continuidad del razonamiento entre turnos; y los bloques `thinking` firmados de Anthropic.

## Portadores por superficie [#carriers-by-surface]

Cada tipo de estado viaja en un portador que los clientes estándar reenvían sin cambios, cuando la superficie tiene uno:

| Estado del proveedor | `/v1/responses` | `/v1/chat/completions` | `/v1/messages` |
| --- | --- | --- | --- |
| Gemini: firma en una llamada de función | sufijo de `call_id` | sufijo de `tool_calls[].id` | sufijo de `tool_use.id` |
| Gemini: firma en una respuesta de texto | elemento `reasoning` del gateway | sólo `provider_specific_fields` | no se transporta |
| OpenAI: reasoning cifrado | elemento `reasoning` nativo | sólo `provider_specific_fields` | no se transporta |
| Anthropic: bloques `thinking` firmados | elemento `reasoning` del gateway | sólo `provider_specific_fields` | bloques `thinking` nativos |

`provider_specific_fields` es una extensión al estilo de LiteLLM que los clientes estándar (Vercel AI SDK, los SDK de OpenAI, el Agents SDK) descartan, así que el estado que sólo viaja ahí se pierde para ellos. Usa `/v1/responses` para conversaciones de varios turnos con modelos de razonamiento.

## Firmas de pensamiento (vinculadas a llamadas de herramientas) [#thought-signatures-tool-call-bound]

Cuando una llamada de herramienta upstream lleva una firma de pensamiento, el gateway la incorpora en el **id de llamada de herramienta pública**, compatible con LiteLLM:

```
<id>__thought__<signature>
```

La identificación con sufijo aparece como `tool_calls[].id` en `/v1/chat/completions`, como `function_call.call_id` en `/v1/responses` y como `tool_use.id` en `/v1/messages` (sin streaming y streaming). Debido a que cada cliente estándar repite los identificadores de llamadas de herramientas palabra por palabra (incluso los clientes que eliminan campos desconocidos, como Vercel AI SDK), la firma sobrevive al viaje de ida y vuelta sin que el cliente comprenda nada.

La firma también se refleja en la llamada de herramienta renderizada para clientes enriquecidos:

```json
{
  "id": "call_1__thought__EjQKMg...",
  "type": "function",
  "function": { "name": "get_weather", "arguments": "{}" },
  "extra_content": { "google": { "thought_signature": "EjQKMg..." } },
  "provider_specific_fields": { "thought_signature": "EjQKMg..." }
}
```

El nivel de mensaje/respuesta agrega además `provider_specific_fields.thought_signatures: [...]`.

### Prioridad de entrada [#inbound-precedence]

En la reproducción, el gateway acepta la firma en cualquiera de las tres formas, combinadas en este orden (las fuentes posteriores ganan por clave):

1. El sufijo de identificación `__thought__` (en `tool_calls[].id`, `function_call.call_id` o `function_call.id`, `tool_use.id`).
2. `provider_specific_fields.thought_signature` en el bloque de llamada de herramienta / `tool_use`.
3. `extra_content.google.thought_signature` (solo superficies con forma de OpenAI).

El sufijo se elimina antes de que algo llegue a un flujo upstream: los adapters siempre ven identificadores limpios y las referencias de resultados de herramientas (`tool_call_id`, `function_call_output.call_id`, `tool_result.tool_use_id`) se eliminan simétricamente para que la coincidencia de llamada/resultado siga funcionando.

### Notas [#notes]

- Las firmas son base64 estándar (`A-Za-z0-9+/=`), que no pueden contener `_`; el separador no es ambiguo.
- Los identificadores pueden exceder los 64 caracteres. El gateway nunca trunca este portador sin pérdidas; los clientes que trunquen los identificadores de llamadas de herramientas perderían la firma. LiteLLM utiliza el mismo esquema en producción.
- Con llamadas a funciones paralelas, Gemini puede firmar sólo la primera llamada; sólo las llamadas firmadas obtienen un sufijo.
- Para el historial de Gemini 3 migrado o ya persistente donde faltan todos los operadores, el adapter de Google aplica el centinela documentado `skip_thought_signature_validator` de Google a la primera llamada de función en ese paso. Siempre se prefieren las firmas exactas; el centinela es sólo una ruta de recuperación de compatibilidad en el límite del proveedor.

## Reasoning cifrado OpenAI (vinculado a mensajes) [#openai-encrypted-reasoning-message-bound]

Para los modelos OpenAI con capacidad de reasoning, el gateway solicita `include: ["reasoning.encrypted_content"]` en sentido upstream y siempre llama al nivel upstream con `store: false` (OpenAI solo devuelve reasoning cifrado para respuestas no almacenadas; el gateway nunca utiliza almacenamiento upstream persistente). Un WebSocket Responses en vivo puede usar el cache de respuesta anterior de conexión local de OpenAI, pero los identificadores de respuesta públicos y ascendentes permanecen separados.

Por superficie:

- **`/v1/responses`**: el reasoning cifrado se representa como elementos de salida nativos `reasoning`, con `encrypted_content` cuando la solicitud incluye `reasoning.encrypted_content`, igual que en OpenAI. Los clientes que reproducen elementos de salida (lo hace el Vercel AI SDK) lo reproducen automáticamente; en la entrada, los elementos `reasoning` con `encrypted_content` se reproducen en sentido upstream antes de las llamadas a funciones que preceden.
- **`/v1/chat/completions`**: transportado como `provider_specific_fields: { "openai": { "reasoning": [{ "id", "encrypted_content", "summary" }] } }` a nivel de mensaje en el mensaje del asistente (y delta de streaming). Los clientes estándar eliminan este campo, por lo que el reasoning cifrado no los utiliza en esta superficie, la misma limitación que LiteLLM.
- **`/v1/messages`**: no compatible: el formato del protocolo de Anthropic no tiene ningún campo de extensión a nivel de mensaje que los clientes hagan eco.

## Firmas de Gemini en respuestas de texto (vinculadas al mensaje) [#gemini-signatures-on-text-responses-message-bound]

Gemini también puede firmar una respuesta sin llamada de función. La firma llega en la última parte, a menudo una parte de texto vacía al final del stream:

```json
[
  { "text": "**Defining the goal**…", "thought": true },
  { "text": "Hello!" },
  { "text": "", "thoughtSignature": "EsAKCr0KAWkU…" }
]
```

En `/v1/responses`, cuando la solicitud incluye `reasoning.encrypted_content`, el gateway sella esas partes en un elemento `reasoning` adicional, después del último elemento de su turno:

```json
{ "type": "reasoning", "id": "rs_…", "summary": [], "encrypted_content": "bfrs_1.eyJ2Ijo…" }
```

- **Sellado, no almacenado.** El valor se cifra con el keyring de cifrado del gateway (AES-256-GCM): los clientes no pueden leerlo ni alterarlo, y no se guarda nada en el servidor. Aparece aunque Gemini no haya devuelto un resumen de pensamiento visible, y el elemento de resumen, si existe, no cambia.
- **Reenviado por clientes estándar.** Los clientes que devuelven los elementos de salida (el Vercel AI SDK con `store: false`, el OpenAI Agents SDK) lo reenvían sin saber qué es.
- **Restaurado en su propio mensaje.** El gateway abre el elemento en el borde y restaura las partes en el mensaje del asistente con el que se emitió: el elemento de mensaje cuyo `id` nombra o, si el cliente descarta los ids, el mensaje del asistente inmediatamente anterior. Nunca se reenvía upstream; si el enrutamiento recurre a otro proveedor, éste lo ignora.
- **Los mensajes editados lo pierden.** Si el texto del mensaje ya no coincide con las partes firmadas, el gateway envía el texto del cliente sin firmas.
- **Sin caducidad ni errores.** Las conversaciones duran meses, así que los elementos no caducan. Uno que no se puede abrir (su clave se retiró de `ENCRYPTION_KEYRING`, fue manipulado o su versión es desconocida) se descarta con un aviso y la solicitud sigue sin él. Los descartes se cuentan en `bifrost_message_state_discarded_total` por `reason`.
- El elemento de mensaje conserva `provider_specific_fields.google.content_parts` para los clientes al estilo de LiteLLM. Si llegan ambos, gana el elemento `reasoning`.

## Bloques de pensamiento de Anthropic (vinculados al mensaje) [#anthropic-thinking-blocks-message-bound]

Claude devuelve bloques `thinking` y `redacted_thinking` firmados. Anthropic exige que el razonamiento de un turno con herramientas vuelva junto con los resultados, y en Claude Fable 5.1, Opus 5.5, Sonnet 5.5 y Haiku 5.5 vincula cada bloque a todo el contenido anterior: un turno del asistente debe volver exactamente como se devolvió, incluido el orden de los bloques, o una solicitud posterior falla con `400` ("The block is bound to a different conversation").

En `/v1/responses`, cuando la solicitud incluye `reasoning.encrypted_content`, el gateway sella el contenido completo del turno (bloques de pensamiento, texto y `tool_use`, en orden) en el mismo tipo de elemento `reasoning`, después del último elemento del turno. Un turno que sólo llama herramientas también lo recibe: nombra el primer `call_id` del turno en lugar de un elemento de mensaje.

- **Reenviado tal como se devolvió.** Al reenviarlo, el gateway manda el turno a Anthropic como un único mensaje del asistente con los bloques originales, siempre que su texto y sus llamadas de herramienta no hayan cambiado. Un turno que el cliente editó se reconstruye a partir de los elementos del cliente, con el pensamiento primero, como antes.
- **Sin huecos.** Anthropic acepta pensamiento recortado desde el inicio de una conversación, no un hueco en medio. Cuando un portador no se puede abrir, el gateway también descarta el pensamiento de todos los turnos anteriores.
- El elemento de mensaje refleja `provider_specific_fields.anthropic.thinking_blocks` y `content_blocks` para los clientes al estilo de LiteLLM, y `/v1/chat/completions` lleva los mismos campos. Un turno que sólo llama herramientas no tiene elemento de mensaje donde reflejarlos.

## Almacenamiento [#storage]

Nada de esto utiliza la base de datos. La tabla `response_states` solo persiste las respuestas que el cliente almacena explícitamente (`store: true` en `/v1/responses`) para el encadenamiento `previous_response_id`/`item_reference`.
