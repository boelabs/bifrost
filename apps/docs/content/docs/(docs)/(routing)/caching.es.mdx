---
title: "Cache de respuestas"
description: "Reutiliza respuestas completas en Redis mediante una opción por solicitud."
---
Bifrost puede almacenar en cache las respuestas completas en Redis y atender solicitudes repetidas idénticas sin contactar a un proveedor. Está **optado por solicitud** y **desactivado de forma predeterminada**: nada se almacena en cache a menos que el cliente lo solicita.

Para conocer la reutilización de solicitudes del proveedor y los contadores de tokens, consulta [Prompt caching del proveedor](/es/docs/provider-prompt-caching).

## Habilítelo por solicitud [#enable-it-per-request]

Envía los headers de cache en la solicitud de inferencia:

| header | Valores | Efecto |
|---|---|---|
| `x-unified-cache` | `true` o `1` | Habilita el caching para esta solicitud. Cualquier otro valor (o ausente) = sin cache. |
| `x-unified-cache-ttl` | segundos | Es hora de vivir de una entrada almacenada. Predeterminado `300` (5 min), máximo `86400` (24 h). |

```bash
curl -X POST $BASE/v1/chat/completions \
  -H "Authorization: Bearer sk-..." \
  -H "x-unified-cache: true" -H "x-unified-cache-ttl: 600" \
  -H "content-type: application/json" -d '{
    "model": "general",
    "messages": [{ "role": "user", "content": "Capital of France?" }]
  }'
```

La primera llamada es perdida (entregada por el proveedor y almacenada); llamadas idénticas dentro del TTL son visitas realizadas desde Redis. Un acierto de cache se registra en `gateway_operations` con `cache_hit = true` y se factura como costo cero.

## Cómo se define el alcance de las entradas [#how-entries-are-scoped]

- **Por virtual key.** El espacio de nombres de la cache es la identificación de la virtual key, por lo que una clave nunca ve las respuestas almacenadas en cache de otra clave.
- **La master key nunca se almacena en cache.** El tráfico del operador siempre va al proveedor, incluso con el header configurado; esto evita que las llamadas administrativas y de prueba contaminen las cachés de los clientes.
- **Por solicitud exacta.** La clave se deriva del tipo de llamada, el espacio de nombres y un hash de la solicitud canonical, por lo que cualquier cambio en el mensaje, el modelo o los parámetros es una entrada diferente.
- **Límite de tamaño.** Los Responses de más de 512 KB (normalmente grandes lotes de incrustación) se publican normalmente pero **no** se almacenan; el ahorro por visita no justifica la memoria de Redis y rara vez se repiten de forma idéntica.
- **No para transmisión, llamadas de herramientas ni solicitudes con estado.** La elegibilidad requiere una solicitud no transmitida, sin herramientas y sin estado del lado del servidor (por ejemplo, una llamada `/v1/responses` con `store: true`): una solicitud de transmisión siempre se activa. Las entradas de contenido multimodal también evitan el caching porque una URL remota puede cambiar sin cambiar la solicitud y los archivos base64 son claves de cache deficientes. Consulta [Streaming](/es/docs/streaming) y [Entradas de contenido](/es/docs/file-inputs).
- **Un hit es gratis.** Se registra con `cost: null` y nunca toca los contadores de gasto o TPM de la virtual key; consulta [Contabilidad de costos](/es/docs/cost-accounting).

## Invalidar [#invalidate]

Los operadores pueden borrar las entradas almacenadas en cache con la master key:

```bash
# Everything
DELETE /admin/cache

# Narrow by call type and/or namespace (a virtual key id)
DELETE /admin/cache?callType=chat&namespace=<virtual-key-id>
```

Ambos filtros son opcionales; omitirlos amplía la coincidencia. La respuesta informa cuántas entradas se eliminaron. Las inscripciones también caducan por sí solas una vez transcurrido el TTL.

## Cuándo usarlo [#when-to-use-it]

Buenos ajustes: prompts deterministas o de baja temperatura, consultas de embeddings repetidas, reintentos idempotentes y endpoints de lectura intensa detrás de un cliente compatible con cache. Evítelo para generaciones personalizadas o de alta temperatura donde cada llamada debe ser nueva: deje el header apagado y nunca tocarán el cache.
